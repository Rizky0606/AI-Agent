## Corrections applied 2026-10-13 (after live re-audit), extended 2026-10-14

This report previously overstated several capabilities. The following claims were **wrong** and are corrected here. Evidence: [assessment-2026-10-13.md](assessment-2026-10-13.md).

- **"recover interrupted tasks" — was false, now fixed (2026-10-13).** `recoverInterruptedTasks()` was called without a `queue` argument, and only enqueued `if (queue)`, so a task left `running` by a worker restart was recovered cosmetically and then hung forever. Verified live before the fix: forced `running`/`progress=40`, worker restarted, `recoveredCount: 1` logged, `task.resumed` written, still `running`/`progress=40` after 40 seconds. Fix: `createAgentWorker` builds and returns the `BullMqTaskQueue`, `startWorkerProcess` passes it through, and the `queue` parameter is now required. Verified live after the fix: task forced `running`/40 with its BullMQ job deleted from Redis, worker restarted, final state `completed`/`progress=100`.
- **Memory was never mentioned here, and it did not work — now durable (2026-10-13).** The `memories` table had no migration, so `to_regclass('public.memories')` was null in production, and the repository swallowed the failure and fell back to a per-process store: `POST /v1/memories` returned 201 and the row vanished on the next API restart (verified live: count=1 → restart → count=0). Fix: migration `0007_memories.sql` creates the table with `vector(1536)` and indexes, and the silent fallback is gone. Verified live after the fix: count=1 → `docker compose restart api` → count=1. Semantic search remains inactive because 9Router exposes no embedding provider (`No credentials for provider: openai`), and there is still no retention sweeper.
- **"Coding tasks do not run lint/typecheck/test/build" — was false, now fixed (2026-10-13).** `createDefaultEnvironment()` returned `{passed: true}` hardcoded for every check and the worker always used that default, so no lint/typecheck/test/build command ever ran in production. Fix: `LocalCodingEnvironment` (`packages/agent-core/src/coding/local-environment.ts`) runs `node --run <script>` in a real workspace with a timeout and bounded output, `createDefaultEnvironment()` is deleted, and each coding task gets its own git workspace under `CODING_WORKSPACE_ROOT` (named volume `coding-workspaces`, created in the worker image with `node` ownership so a fresh volume is writable). Verified live: a workspace whose `lint` exits 1 ends `failed` with `evaluationResult.score=0.71` and issue `Lint issue: Command failed: node --run lint`; a workspace whose scripts pass ends `completed` with `score=1` and a real git diff artifact.
- **Tool calls completed without any evaluator — now gated (2026-10-13).** `executeRegisteredTool` wrote `completed` directly. It now runs `GenericEvaluator` over the tool result first, attaches evidence only when the tool actually returned data, and emits `task.failed` when the evaluator rejects (`apps/agent-worker/src/task-executor.ts:637-674`).
- **"Research has no search path" — was false, now fixed (2026-10-13).** `web_search` defaulted to `https://example.com/search?q=…` and was registered nowhere, and `ResearchAgent` fell back to a hardcoded MDN/nodejs.org source list plus three hardcoded claims that satisfied the evaluator without a single network call. Fix: `duckDuckGoSearch` (`packages/tools/src/builtin/web-search.ts`) queries the DuckDuckGo HTML endpoint, unwraps its `/l/?uddg=` redirect wrappers, and throws instead of reporting a false "0 results" when the markup is unrecognised or the status is not 2xx; `createDefaultToolRegistry` registers it alongside `web_fetch`. `LocalResearchEnvironment` (`packages/agent-core/src/research/local-environment.ts`) drives search and browse through that guarded registry, so `web:search`/`web:fetch` are permission-checked, and drops any page whose fetch fails, whose text extracts to fewer than 200 characters, or whose output the registry had to truncate. The hardcoded source and claim lists are gone: with no environment the run produces zero sources and the evaluator rejects it. `htmlToText` strips `<script>`/`<style>` bodies so minified JavaScript cannot be cited as prose, and `web_fetch.outputLimitBytes` rose 64 KiB → 1 MiB because above that the registry substitutes a partial-JSON envelope. Verified live: a real query reached `completed` with `score=1` over five fetched pages (temporal.io, learn.microsoft.com ×2, github.com ×2) and five claims each linked to a page that was actually fetched (task `46098f3e-…`); a query with no hits reached `failed` with `score=0` and `Research completion blocked: No valid sources provided` (task `c38ae271-…`); a query where only one source was readable reached `failed` with `score=0.8` on the `cross_check` criterion (task `597838e9-…`). Remaining: claims are page openings, not model synthesis, so relevance to the question is not judged.
- **No production path dispatches commands to a Windows device — fixed 2026-10-13.** `dispatchCommand` had zero callers in `apps/`. A task with `payload.targetDevice` now asks the API for presence and dispatches `command.execute` over the device's WSS session through the token-guarded internal route `POST /v1/internal/device-commands` (`apps/api/src/routes/device-commands.ts`); Caddy answers `404` for `/v1/internal/*`, so only the internal Docker network can reach it. Device commands are HIGH risk and always require approval, and the approval fingerprint covers the command text plus the `deviceId`, so one approval never authorises a different command. The verdict is the device exit code. Verified live: task `954db21a-b14f-44ad-b2c2-49b4a2e99d55` → `waiting_approval` → approve → the device received `command.execute` → `completed` with `exitCode 0` and an artifact holding the device's real `stdout` (`SMOKE-WORKSTATION`); an offline target ends `failed` with `offlineReason: device_unreachable` instead of a false success. Two defects found while verifying live are also fixed: the `/v1/agent/ws` handshake wrote the query-string `deviceId` into the uuid column `devices.id` without validation, so a real agent id (`win-dev-<hash>`) raised `22P02` as an unhandled rejection and killed the API process (that write is gone, and `GET /v1/devices` now reports registered rows with presence from live sessions); and a task failing straight from `queued` violated the task state machine (`IllegalTaskStateTransitionError`), leaving it `queued` forever with no visible error, so the offline path now transitions through `planning`. Still open: device sessions remain in memory, and the command allowlist has never run on real Windows hardware (see the next entries).
- **"Device identity is cryptographic" was false — now true (2026-10-14).** `devices.public_key` was in the schema but never populated or verified, and the device id came from the `/v1/agent/ws` query string, so any client could claim to be any device. Fix: the server sends `device.challenge` (32 random bytes), the agent signs it with a P-256 private key it keeps in webview `localStorage` (`apps/windows/src/connection/device-key.ts`), and the server verifies the signature with `crypto.verify(..., { dsaEncoding: 'ieee-p1363' })` (`apps/api/src/services/device-identity.ts`) before creating the session; a `deviceId` in the query string is refused with `DEVICE_IDENTITY_REQUIRED` rather than trusted. The device id is now the uuid the server issues in `device.handshake_ack`, and `devices.public_key` stores the canonical JWK under a partial unique index (`devices_public_key_uq`, migration `0008_device_key_identity.sql`), so the same key always maps to the same row and reinstalling an agent under the same hostname no longer duplicates it. Remaining: the private key lives in webview storage rather than an OS keystore, and device sessions are still in memory, so an API restart drops sessions until devices reconnect (the row and key survive). Verified live: a claimed `deviceId` was refused, a signed handshake returned server-issued uuid `4067f93f-…` with `public_key` stored, reconnecting with the same key returned the identical id while the stale socket was closed, and a `windows_command` task against that id still reached `completed` with `exitCode 0` and the device's real `stdout`.
- **"The Windows agent enforces capability/action/cwd but no command text" — fixed 2026-10-14.** `CapabilityRegistry` gated which capability was on and where it could run, but any PowerShell command was accepted inside an allowed working directory once a capability was enabled. Fix: `assertCommandAllowed` (`apps/windows/src/security/command-allowlist.ts`) parses the command text, extracts the program being called, and refuses anything outside the allowlist with `COMMAND_NOT_ALLOWED` plus a named reason and the offending token; it runs in `CommandExecutor` and `TauriCommandExecutor` before any spawn, and the Rust backend re-checks in `execute_local_command` (`apps/windows/src-tauri/src/command_allowlist.rs`). The allowlist comes from the same local `CapabilityRegistry` rules the capability flags live in, so an inbound task payload cannot widen it; a capability with no allowlist (for example `git`) refuses every command text. Deny by default, with `hostname` plus the programs this repo's own tests exercise; chains (`;`, `&&`, `||`, `|`), subshells, `-EncodedCommand`, `Invoke-Expression`/`iex`, shell wrappers (`cmd`, `powershell`, `wscript`, `bash`, `wsl`), the call operator `&`, and path- or extension-qualified program names are all refused. Verified by `apps/windows/test/command-allowlist.test.ts` (13 tests) and `cargo test --offline` in `apps/windows/src-tauri` (5 tests). **Evidence limit: this was never exercised on real Windows hardware, only in unit tests.**
- **An approved device command was lost when the agent reconnected after an API restart — fixed 2026-10-14.** Device sessions live in API process memory, so a restart made an online device look offline; a dispatch then failed immediately and the approval the user had just granted was burned, forcing a second approval for the same command. Fix: `DeviceConnectionManager.waitForConnection` lets a dispatch wait for the agent to dial back, bounded by `DEVICE_RECONNECT_GRACE_MS` (default 30 s), and `TaskExecutor` computes `resumedWithApproval` before the presence gate so an already-approved command skips that gate entirely. Covered by `apps/api/test/device-commands.test.ts` and `apps/agent-worker/test/device-dispatch.test.ts`; both fail when the grace window is zeroed or when the gate ignores the approval, so the tests are load-bearing. Sessions are still not persistent — this is a mitigation, not a fix.
- **"Notifications have never been sent" — fixed 2026-10-14.** `notifications` held 0 rows in production and the API built `NotificationEngine` without storage (`apps/api/src/index.ts:211`), so delivery state lived only in process memory. Fix: the API now constructs `NotificationEngine` with `SqlNotificationRepository` and `createFcmProviderFromEnv()`, and `broadcaster.subscribe(createTaskNotificationListener(...))` (`apps/api/src/services/task-notifications.ts`) turns Redis task events (`task.completed`, `task.failed`, `task.waiting_approval`) into durable `notifications` rows with `delivery_state` and `deep_link`. Notification preferences are durable too. Verified live: a scheduled `smoke.echo` task produced `task_completed`/`delivered`; a `windows_command` task against an offline device produced `task_failed`/`failed` with a truthful `last_error`; a `task.waiting_approval` event published on the real channel `personal-ai-os:events:all` produced `approval_required`/`failed` with `personal-ai://approvals/appr-proof-1`; row count and delivery states survived `docker compose restart api`. The duplicate dispatcher in the API process (which enqueued without inserting into `tasks`) was deleted; `tick()` belongs to the `scheduler` container alone.
- **"The FCM provider would fail even with valid credentials" — fixed 2026-10-14.** `apps/scheduler/src/fcm-provider.ts:185` injected `accessToken: 'dummy-env-token'` hardcoded whenever a service account was present. Fix: `HttpFcmProvider` takes an `FcmAccessTokenSource`, and `ServiceAccountTokenSource` signs a JWT with the service account `client_email`/`private_key` (RS256), exchanges it at `token_uri` with `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` and scope `firebase.messaging`, and caches the access token until 60 s before `expires_in`. A service account missing `client_email` or `private_key` yields `DisabledFcmProvider` instead of a literal-token send. Verified against a stub HTTP server (`apps/scheduler/test/fcm-provider.test.ts`, 4/4): cached token reuse, refetch below the margin, hard failure on a rejected exchange, and `Authorization: Bearer <real token>` on the FCM request. The literal is gone. Push tokens live in `devices.push_token` (migration `0009_device_push_token.sql`, partial unique index) and are registered per install via `POST /v1/devices/:deviceId/push-token` (204/404/400 verified live). Still open: no real send to Google (`FCM_SERVICE_ACCOUNT_JSON` is not provisioned), and no dead-letter queue when a push exhausts `maxAttempts`.
- **"`audit_logs` covers only approvals" — fixed 2026-10-14.** Production held 10 rows, all `approval:approved|denied`, and tool, MCP, browser, and artifact actions were not recorded; MCP audit went to `console.log` only. Fix: `SecuredCapabilityGuard` (`packages/permissions/src/guard.ts`) writes **one `audit_logs` row per call, after the outcome is known** (`metadata.outcome` `success`/`failure` plus `durationMs`/`error`), and both processes pass it an `auditLogger` (API `apps/api/src/index.ts`, worker `apps/agent-worker/src/index.ts`). Artifact writes are audited through `ArtifactManager.auditSink` (`packages/tools/src/artifacts/artifact-manager.ts`), used by API and worker, so one sink covers both. `audit_logs.resource_id` became `varchar(512)` (migration `0010_audit_resource_id_text.sql`) because tool calls write paths, URLs, and tool names into it, which the previous `uuid` column rejected with `22P02`. A failing audit sink never changes the result the caller sees — the side effect already happened, so turning it into an error would invite a retry that runs it twice. MCP tool calls already go through the guard (`action: tool:mcp_<server>_<tool>`, `resource_type: external_mcp`), so MCP audit no longer goes to `console.log` only; that sink was deleted. Verified live: `audit_logs` holds 38 rows including `web:fetch`/`web:search` (tool calls), `tool:mcp_echo_echo` (MCP call), `browser:navigate` (browser action), and `artifact:write`, and the SSRF fetch to `169.254.169.254` is recorded as `allow | failure` with its real error message rather than a bare `allow`.
- **`AiCouncil` and `SelfHealingEngine` were dead code — removed 2026-10-14.** Both had tests that passed and zero call sites in `apps/`, so they were deleted rather than wired up: the `council/` and `healing/` subdirectories of `agent-core`, their two `export *` lines in `packages/agent-core/src/index.ts`, and both test files. Package tests fell 40 → 31 and `tsc --build` stayed clean. The three runtime stubs (`UnverifiedRuntimeAdapter`, `HermesRuntimeAdapter`, `OpenHandsRuntimeAdapter`) went the same way — they claimed Hermes refuses to execute, which was never true of the production path (`RemoteRuntimeAdapter` → `apps/runtime-bridge`), so they were misleading as well as unused.
- **"Nothing verifies schema ↔ migration parity" — fixed 2026-10-14.** `schema.ts` declared a `memories` table that no migration created (production ran without it) and an unused `artifacts` table that no migration created either; both were only ever found by manual audit. ## Implemented

- Worker and scheduler standalone entrypoints remain alive, handle SIGTERM/SIGINT, close durable clients, and recover interrupted tasks by re-enqueuing them (fixed 2026-10-13; see the correction above).

- Production worker now constructs one guarded `ToolRegistry`; API constructs the catalog registry with the same built-in registration policy.
- Explicit generic `payload.toolName` tasks execute through `ToolRegistry.executeTool`, persist `task.tool_call`, checkpoint output, and complete **only after `GenericEvaluator` accepts the tool result**. A tool that returns `undefined`/`null` fails instead of completing. Approval-required tool calls persist a waiting checkpoint, resume the same task, and revalidate/consume approval before execution; verified by regression test, not production smoke.
- Generic natural-language tasks (`kind` starting with `generic`, no `toolName`, no `useRuntime`) now execute through the real path: `IntentAnalyzer` → `Planner` → `ModelGateway.chat` (model from `payload.model`, else `DEFAULT_CHAT_MODEL`), guarded by `PermissionEngine` under `model:chat`. Step-4 evaluator evidence is derived from the actual model output, tool result, or checkpoint state — the fabricated `matchCount: 3` / `result: 'ok'` / `'Task berhasil diselesaikan…'` evidence is gone for non-simulated tasks. `isSimulation: true` retains placeholder behaviour.
- Generic tasks fail closed: no `ModelGateway` or no resolvable model → task `failed` with `requires a ModelGateway` / `requires payload.model or DEFAULT_CHAT_MODEL`; no synthetic completion.
- Generic orchestration contract (`kind` starting with `generic`, no `toolName`, no `useRuntime`): `payload.prompt` / `payload.instructions` / `payload.goal` supplies the instruction (falling back to `task.kind`); `payload.model` selects the model (else `DEFAULT_CHAT_MODEL`); `payload.workspaceId` scopes the run (defaults to the task id); `payload.acceptanceCriteria` overrides the default single `task_output` artifact criterion. Every field is optional. `payload.mode` (`auto|fast|coding|complex|research`) is forwarded to the router but only `coding` has an observable effect: it sets `task.started.selectedRuntimeId` to the preferred runtime (observed `omp`). The persisted `task.started.intent` and `runtime` come from `IntentAnalyzer` on the prompt, not from `mode` — observed with `mode: 'research'`, which still reported `intent: 'simple_chat'` / `runtime: 'fast_model'`.
- `task.completed` now carries the real `evaluationResult` for the generic path; `task.tool_call.input` records the actual prompt instead of a hardcoded query.
- Resuming a task whose checkpoint is `stepIndex: 2` / `lastExecutedAction: waiting_approval` / `actionState.approved: true` replays the guarded step-2 action with the approval id, so the approved capability executes exactly once rather than being skipped.
- Production registry exposes `web_fetch` and `web_search`; the worker additionally registers `browser_navigate` because it owns the Playwright runner. `save_artifact` stays unregistered until the artifact runtime dependency is wired.
- `/v1/catalog` now includes registered `ToolRegistry` metadata when a registry is injected, alongside skills.
- Android attachment UI no longer creates `https://placeholder.local/image.png`; explicit unavailable state rendered. No upload contract exists.
- Capability matrix: `docs/capability-matrix.yaml`.
- Both clients sign in with Google instead of pasting a JWT (2026-10-14). Authorization Code + PKCE with the token exchange on the server: `GET /v1/auth/google/start` signs a state blob (redirect target, client state, client challenge, server-side PKCE verifier) and redirects to Google, `GET /v1/auth/google/callback` verifies the ID token against Google's JWKS (issuer, audience, `email_verified`) and redirects back with a one-minute login code bound to the client's challenge, and `POST /v1/auth/exchange` redeems it for the usual token pair. Migration `0011_user_identities.sql` adds `user_identities` and makes `users.password_hash` nullable, because a provider-only account has no password; a verified email reuses the existing user row, so a password login and its Google login stay on one user id. Android uses `expo-crypto` PKCE and the `personal-ai://auth` deep link; the Windows agent binds a loopback listener in the Rust `google_login` command, opens the system browser, persists the session, and refreshes once on `401`. With `GOOGLE_CLIENT_ID`/`SECRET`/`REDIRECT_URI` unset the routes answer `503 NOT_CONFIGURED` rather than half-working. Verified end to end against production with a real Google account (see `docs/final-audit.md` §8.F Cacat 16).

### Chat contract and lifecycle (2026-10-14)

- Account-authenticated `POST /v1/chat` and `/v1/chat/ws` use optional `conversationId`, `projectId`, `workspaceId`, `model`, `mode` plus required `content`. New conversations omit `conversationId`; the server creates the durable ID, not a client placeholder. WebSocket sends wait for `{type: 'auth.ok', userId}`.
- Stream frames: `{type: 'conversation.created', conversationId}`; `{type: 'message.created', conversationId, message: {id, conversationId, role, content, createdAt, metadata?}}` for the persisted user message and empty assistant message; `{type: 'message.delta', conversationId, messageId, delta}`. The assistant ID remains identical across creation, deltas, persistence, and terminal frames.
- Terminal frames are `{type: 'message.completed' | 'message.cancelled', conversationId, messageId, message}` with the saved message; completion also carries `usage`, `resolvedModel`, `mode`. `{type: 'chat.cancel', messageId?}` cancels one stream (all socket streams when omitted); cancellation persists accumulated partial content with `metadata.cancelled: true`, including provider abort exceptions. Errors use `{type: 'error', code, message, conversationId?, messageId?}`.
- `GET /v1/conversations` returns `{conversations}` across the authenticated account (optional `projectId` filter); `GET /v1/conversations/:conversationId/messages` returns `{messages}` after ownership checks. Android and Windows hydrate saved history, reconcile live messages by stable IDs, retain failed-send drafts for explicit retry, and show connection/provider errors rather than fabricated replies. Retry is not an exactly-once delivery guarantee.
- Windows `ChatConnection` uses a separate account-only `/v1/chat/ws` socket, gated by `auth.ok`; chat requires neither device registration nor device command permissions. Device execution stays on its separate signed device channel.
- Verification passed: API/Windows/Android typechecks and lint; Windows tests (35 passed, 4 platform skips); Android tests (28 passed). `apps/api/test/chat-lifecycle.test.ts` passed against a real Fastify TCP listener and native WebSocket, exercising actual Android/Windows chat transports, user/assistant frames, stable IDs, HTTP history, auth race, cancellation (including abort exceptions), input errors, failed partial persistence, and Android draft restoration/hydration. The model gateway is an explicitly labeled deterministic test double; storage is in-memory. No hardware, production-model, PostgreSQL restart, or exactly-once retry verification is claimed.
